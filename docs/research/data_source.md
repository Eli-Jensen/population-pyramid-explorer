## (b) UN Data Portal API (https://population.un.org/dataportalapi/api/v1/)
- Metadata endpoints are OPEN (no auth), probed 200: /indicators (86 indicators, paged: pageNumber/pageSize/pages/total/nextPage URL), /indicators/{id}, /locations (300 locations incl. aggregates; iso3/iso2/lat/long; 60 pages at pageSize=5, i.e. pageSize param works), /locations/{id}, /sources (31 sources; WPP 2024 = sourceId 27).
- Relevant indicator IDs (all sourceYear 2024): 46 "Population by 5-year age groups and sex" (PopByAge5AndSex, 1 July, 0-4..95-99,100+, persons), 47 "Population by 1-year age groups and sex" (PopByAge1AndSex), 49 Total population by sex, 67 Median age, 70/71 broad age groups, 72 sex ratio. dimAge/dimSex/dimVariant=true on 46/47.
- DATA endpoints REQUIRE A BEARER TOKEN: GET /data/indicators/46/locations/392/start/2026/end/2026 -> HTTP 401, header `www-authenticate: Bearer` (also for ?format=csv). Token is free, obtained by emailing population@un.org with subject "Data Portal Token Request" (documented by third parties, e.g. https://github.com/jdebacker/Population-Data; the UN's own /dataportal/about/dataapi page is a JS SPA that returns nothing to fetchers). No swagger at /swagger/*. Rate limits: not published; the data endpoint is paged like metadata (pageSize/pageNumber). Verdict: irrelevant for this project — the bulk CSV.gz has everything and needs no token; the API is per-location/per-indicator and slower than one 30-67 MB download. Its citation string is literally the same WPP 2024 citation.

## (d) Entity coverage
Raw WPP2024_PopulationByAge5GroupSex_Medium.csv.gz has 555 LocIDs: 237 Country/Area (ALL 237 have ISO3_code — Kosovo = XKX, Taiwan = TWN; the "no ISO3 for Kosovo" worry is obsolete in WPP2024) + 1 World + 7 Geographic regions + 21 Subregions + 9 SDG regions + 9 Income groups + 7 Development groups + 7 "Special other" (LLDC/SIDS splits) + 23 "Ad Hoc groups" + 234 rows with LocTypeName NaN (ADB/ECA/ECE/ESCAP/ESCWA/AU/BRICS/EU/G7/G20/IPCC AR6/Belt-Road/etc. special aggregates, LocID 1000-98999 + 5507-5523).
Special cases (footnotes in XLSX NOTES sheet):
- LocID 158 "China, Taiwan Province of China", ISO3 TWN, note 8 (China note 5: China excludes HK, Macao, Taiwan). populationpyramid.net keeps it under the WPP2019 label "Other non-specified areas" (slug /other-non-specified-areas/) — a politically-evasive relic; recommend displaying "Taiwan" (with UN name in a tooltip/metadata).
- LocID 412 "Kosovo (under UNSC res. 1244)", ISO3 XKX (user-assigned code, not ISO official), note 23; Serbia (688, note 24) excludes it. populationpyramid.net OMITS Kosovo entirely (1.67M people). Recommend include.
- Channel Islands: WPP2024 splits Guernsey (831, GGY, 64.6k) and Jersey (832, JEY, 104k), note 19 (Crown dependencies); populationpyramid.net still lists "Channel Islands" LocID 830 whose API returns an EMPTY series — a broken legacy row. Isle of Man 833 IMN 84k.
- Holy See (336, VAT): 509 persons in 2026 — the only entity < 1,000. Western Sahara (732, ESH, 2026 pop ~600k) present, no note. Under 10k persons in 2026: 8 entities (Holy See, Niue 1.8k, Tokelau 2.7k, Falklands 3.5k, Montserrat 4.3k, Saint Helena 5.2k, Saint Pierre & Miquelon 5.5k, Tuvalu 9.4k); under 100k: 38.
- populationpyramid.net: 236 entities = 200 WPP countries + 36 aggregates (World 900, regions/subregions 903-957 incl. legacy 921 South-Central Asia & 947 Sub-Saharan Africa, development groups 901/902/934/941/948, 5500/5501 Central/Southern Asia). It drops 37 WPP countries: every entity under ~83k people (smallest kept = US Virgin Islands 83.4k) plus Andorra 84k, Isle of Man, Jersey, Kosovo — i.e. a frozen legacy list, not a rule. Its API (https://www.populationpyramid.net/api/pp/{LocID}/{year}/?csv=true) returns WPP 5-year bins in persons (Japan 2026 0-4 M=1,968,258 matches WPP 1968.258k exactly), keyed by WPP LocID; no income/SDG groups.
Recommended inclusion rules for the new tool:
1. Include all 237 Country/Area (keyed by ISO3, keep LocID as secondary key for API/site interop). Flag `pop_total_2026 < 50k` as "micro" and default the similarity search to exclude micro entities (tiny pyramids are noisy/lumpy: Holy See has ~5 people per single-age bin) with a toggle to include them.
2. Include a curated aggregate set as separate "region" entities, default-excluded from similarity results but selectable as the query: World 900; 7 geographic regions + 21 subregions (LocTypeName in Geographic region/Subregion); 8 SDG regions; the 4 World-Bank income groups (1500/1501/1502/1503); LDC 941, More/Less developed 901/902. Skip Ad Hoc / special-agency aggregates (234+23 rows) — they are politically defined and redundant. Aggregates need `LocID`-keyed ids (no ISO3); use `agg:{LocID}` or the SDMX code.
3. Never mix 1 July and 1 January files; use 1 July (matches populationpyramid.net and the Data Portal).

## (e) US Census Bureau International Database (IDB)
- Coverage: 227 countries and areas with population >= 5,000 (misses ~10 WPP micro-entities, Kosovo and Taiwan ARE present); single year of age 0-100+ by sex; totals 1950-2100 but age detail only from each country's base year (varies, often 1980s-1990s) through 2100; July 1 reference; some subnational areas. Last updated Dec 2025, next update planned Nov 2026 (https://www.census.gov/programs-surveys/international-programs/about/idb.html).
- API: https://api.census.gov/data/timeseries/idb/1year (vars NAME,POP,AGE,SEX,YR,GENC) and /5year (126 vars: POP0_4..POP100_, TFR, E0, SEXRATIO...). Requires a free API key (unauthenticated call returns "Missing Key" HTML); key signup https://api.census.gov/data/key_signup.html. Country codes are GENC (2-letter, ~ISO2), not ISO3. Bulk download also available. Terms: US federal work = public domain; API ToS requires the notice "This product uses the Census Bureau Data API but is not endorsed or certified by the Census Bureau." (https://www.census.gov/data/developers/about/terms-of-service.html).
- Worth supporting? Not for v1. It is an independent (not UN-derived) projection, so it would be a genuine second opinion for "how different are two agencies' pyramids for the same country-year" — a nice later feature — but its base-year truncation breaks the 1950-2100 uniformity, GENC->ISO3 mapping is extra work, and the key requirement complicates a static build. Defer; leave a `source` column in the schema so it can be added.
- National single-year sources: only cheap ones are Eurostat demo_pjan (EU/EFTA, single ages, JSON-stat API, no key) and the Human Mortality Database (~41 countries, free registration). Neither adds shape information WPP lacks; skip unless a "compare UN vs national" feature is wanted.

## (g) Recommended ingestion pipeline (new repo, uv/Python, static output for Svelte 5)
Download (pin URLs + sha256 in a manifest; fetch with httpx streaming; keep raw in data/raw/wpp2024/, gitignored):
1. WPP2024_PopulationBySingleAgeSex_Medium_1950-2023.csv.gz + _2024-2100.csv.gz (primary; 5-year bins are then derived by summing, guaranteeing consistency).
2. WPP2024_PopulationByAge5GroupSex_Medium.csv.gz (cross-check only; assert derived 5-year == published within 0.01k).
3. WPP2024_CSV_files_update.zip (Togo patch: replace LocID 768 rows for Medium from the *_Update.csv files).
4. Optional later: WPP2024_PopulationBySingleAgeSex_{High,Low}_2024-2100.csv.gz for a variant switch (~67 MB each).
Normalize:
- Keep entities: LocTypeName == "Country/Area" (237) + curated aggregates by LocID list (see d.2). Emit entities.json: {id, iso3|null, locid, name, short_name (e.g. "Taiwan", "Kosovo"), type, parent_locid, sdmx, note_ids, pop_2026, is_micro}.
- Per (entity, year): arrays male[101], female[101] of shares of TOTAL population (male_i + female_i sums to 1 over both sexes — the pyramid shape people see, mirrored bars), plus scalar total (persons). Also store per-sex-normalized shares only if the similarity metric wants sex-independent shape; otherwise derive in JS. 5-year bins derived client-side by summing 101 -> 21 (cheap), or precompute both.
Sanity checks (fail the build): no negatives; |M+F-T| < 0.002k per row; sum of 101 ages == TPopulationBySex total within 0.01k; exactly 101 ages 0..100 per (loc,year), 151 years per loc; shares sum to 1 ± 1e-6 after float16 rounding (renormalize before casting); open-ended 100+ bin present and last; Togo 2022 total ≈ 8.2M after patch; no duplicate LocIDs; every Country/Area has ISO3.
Output format for the static site (36k pyramids x 202 values):
- Float16 shares: 237 x 151 x 202 x 2 B = 14.5 MB raw; gzip/brotli ~8-10 MB. Too big for one first-load, so split: (1) `pyramids/{entity}.bin` one Float16Array (151 x 202) per entity, 61 KB each, fetched on demand for the viewed country; (2) `year/{year}.bin` all entities for one year (237 x 202 x 2 B = 96 KB) for the same-year similarity search; (3) for "any year" search, ship the precomputed feature/embedding matrix instead of raw pyramids (36k x d float16; d=64 -> 4.6 MB) or run the search offline and ship top-k neighbor tables (36k x 20 x uint16 = 1.4 MB). Decide after the embedding experiment; the raw float16 shards cost nothing extra.
- Use plain little-endian binary + a tiny JSON index (offsets, entity order, years 1950..2100); no Arrow runtime needed in the browser (Float16Array is in all evergreen browsers since 2025; fall back to Uint16 + manual decode if needed). Keep a Parquet of the long table (entity, year, age, sex, pop, share) in the repo for Python-side experiments.
- Shape-only search should use shares, not counts; consider also storing log-shares or age-smoothed 5-year shares to reduce single-age heaping noise in small countries.
Update strategy for WPP2027 (11 Jul 2027) and interim patches:
- manifest.json = {revision: "WPP2024", files: [{name, url, sha256, bytes, last_modified}], patches: ["WPP2024_CSV_files_update.zip"]}; `make data` re-downloads when sha256 changes; all outputs are pure functions of the manifest, so bumping revision to WPP2027 = new file names (pattern WPP{YYYY}_PopulationBySingleAgeSex_Medium_{1950-2026?,2027-2100}.csv.gz — the split year moves with the base year; discover via https://population.un.org/wpp/assets/downloads.json rather than hardcoding), re-run, diff entities.json (expect LocID/ISO changes), re-run sanity checks, regenerate embeddings, publish with revision string in the site footer and the data path (/data/wpp2024/... so old links keep working).
- Watch the downloads.json "Header" for interim updates (grep "Release date"); a monthly CI job comparing Content-Length/Last-Modified of the pinned files catches silent republishes.
